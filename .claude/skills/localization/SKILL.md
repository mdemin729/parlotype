# Localization Skill

Parlotype's interface ships in English, Russian and Spanish, with more to come
([ADR-064](../../../docs/decisions/064-ui-localization-foundation.md)). **Any change to
user-facing text must land in every language in the same change.** A locale left behind
is not a follow-up task — it is a broken build.

## The rule

> Adding, changing or removing UI copy means editing `Strings.resx` **and every**
> `Strings.<culture>.resx`, then regenerating `Strings.cs`.

`pwsh scripts/check-localization.ps1` enforces it, `LocalizationParityTests` enforces it in
CI, and a `Stop` hook blocks a session that ends with it broken.

A **typo'd key is silent** — `{loc:Tr Setings_Theme_Title}` compiles, does not throw, and
renders the raw key name in the window. The check catches it; nothing else does.

## Adding a string

1. **Add the key to `src/Parlotype.Desktop/Resources/Strings.resx`** (the neutral file — it
   *is* English; there is no `Strings.en.resx` and there must never be one).
2. **Add the same key to every `Strings.<culture>.resx`** — currently `ru` and `es`. Check
   `SupportedUiLanguages.All` rather than assuming; the registry is the source of truth.
3. **Regenerate the accessor:** `pwsh scripts/gen-strings.ps1`. Never hand-edit
   `Strings.cs` — it carries an `<auto-generated>` header and is overwritten.
4. **Use it:**
   - In AXAML: `Text="{loc:Tr Settings_Theme_Title}"` with
     `xmlns:loc="using:Parlotype.Desktop.Markup"`. Never a bare literal.
   - In a view model: `Strings.Settings_Theme_Title`.
5. **Verify:** `pwsh scripts/check-localization.ps1`.

## Key naming

`Area_Component_Purpose`, flat, no nesting:

```
Settings_Theme_Title            Onboarding_Recording_Body
Settings_Theme_Description      Transcribe_Status_Recording
Help_HotkeysHeading             Settings_InterfaceLanguage_SystemDetailFormat
```

Match the area prefix already used by neighbouring keys rather than inventing a new one.

## Composite formats — the part that bites

**Numbered placeholders only. Never interpolate a translated string.**

```csharp
// Wrong — the sentence cannot be reordered, and no translator ever sees it.
StatusText = $"Downloading {modelName}…";

// Right — the generator emits a typed helper for any key containing {0}.
StatusText = Strings.Format_Model_DownloadingFormat(modelName);
```

`gen-strings.ps1` produces `Format_<key>(...)` with one parameter per placeholder, so the
wrong argument count is a compile error rather than a `FormatException` in front of a user.

Add a `<comment>` to any key with placeholders saying what each one holds. A translator
seeing `{0} isn't a source in {1}` with no context will guess, and guess wrong.

**Russian and German move word order and inflect nouns.** A sentence with a noun slot often
cannot be translated at all — `"{0} isn't a source in {1}"` needs a grammatical case that
English does not mark. When you hit one, **rephrase the English into a form that survives
substitution** (label-and-value, or a sentence where the placeholder sits at the edge)
rather than handing the problem downstream. That is a copy decision, and it is cheapest
while the English is still in front of you.

## Never split a sentence across markup

A `TextBlock` built from several `<Run>`s with bound values between them cannot be
translated — the word order is frozen by the markup:

```xml
<!-- Wrong: five Runs around two bound names. No translator can reorder this. -->
<TextBlock>
  <Run Text="This session is already running the" />
  <Run Text="{Binding LoadedRuntimeName}" FontWeight="SemiBold" />
  <Run Text="runtime. Restart to switch to" />
  <Run Text="{Binding SelectedRuntime}" FontWeight="SemiBold" />
</TextBlock>

<!-- Right: one composite format on a view-model property. -->
<TextBlock Text="{Binding RestartRequiredNote}" />
```

The cost is per-run formatting (bold on the substituted values). Pay it — a sentence
that only works in English is worse than one without bold. If the emphasis is truly
load-bearing, restructure the copy so the emphasised part is its own label.

## Keyboard key names stay; the words around them do not

"Ctrl", "Alt", "Shift", "Win", "Space" are printed on the user's keyboard and Windows
leaves them alone in every language. Only the prose around them is translated — and it
must be a **format**, never a concatenation, because languages disagree about where the
words go:

| | side + key | verb + key |
|---|---|---|
| English | `Right Ctrl` | `Hold Right Ctrl` |
| Russian | `правого Ctrl` (genitive) | `Удержание правого Ctrl` |
| Spanish | `Ctrl derecho` (**after**) | `Mantener Ctrl derecho` |

`HotkeyText` (Desktop) does this. Core's `HotkeyGesture.DisplayString` is deliberately
*not* localized: the hotkey log lines write it, and a log that changes language with the
UI cannot be grepped.

## What is NOT localized

Leave these in English — they are developer- or protocol-facing, or they are identifiers:

- log messages and exception messages
- engine, model and runtime names: `Whisper`, `Parakeet TDT v3`, `Vulkan`, `gpt-4o-mini-transcribe`
- file names and paths: `settings.json`, `%LOCALAPPDATA%`
- benchmark CLI output (Spectre.Console tables)
- **speech** source/target language names — those come from ICU via `CultureInfo`, not
  from resx. Around 99 names times N locales is not a translation task we own.
- language rows in the interface-language picker: they are **endonyms** ("Русский"), so
  someone stranded in a language they cannot read can still find their own.

## Live switching — what updates itself and what does not

Text bound through `{loc:Tr}` or `Localizer.Entry` re-reads automatically when the language
changes. **Copy composed in C# does not.** If a view model builds a label in its
constructor — display-item titles, summary sentences, anything captured into a field —
override the hook:

```csharp
protected override void OnCultureChanged()
{
    base.OnCultureChanged();          // re-raises Title
    foreach (var item in Options)
        item.RefreshDisplayName();
}
```

`SettingsWindowViewModel` already rebuilds the navigation list on the same event, because
nav rows are snapshots of `Section.Title`.

## Translation quality bar

- Hold the English register: terse, sentence case, no exclamation marks.
- Keep one term per concept across the whole file. The Russian terminology sheet lives in
  `plans/2026-09-05-ui-localization/`; extend it rather than improvising a synonym.
- Never translate an identifier the user sees verbatim elsewhere (`Parakeet TDT v3`,
  `Vulkan`, `settings.json`, `Esc`).
- Use the locale's own typography: `«…»` in Russian, `¿…?` / `«…»` in Spanish, a
  non-breaking space before units (`{1} с`).
- If you genuinely cannot translate a string, say so in your summary. Do not paste the
  English in as a placeholder — `NoKeyIsAccidentallyUntranslated` will fail, and correctly.

## Adding a new language

1. Add a row to `SupportedUiLanguages.All` in `src/Parlotype.Core/Localization/` —
   `new("de", "Deutsch")`, endonym spelled as that language spells it.
2. Create `src/Parlotype.Desktop/Resources/Strings.de.resx` with **every** key.
3. `pwsh scripts/check-localization.ps1` — it will name anything missing.
4. Render the settings screenshot tests under the new culture and read the images. German
   runs ~35 % longer than English; fix clipping by making controls content-sized, never by
   shortening the translation.

Nothing else changes: no markup, no view models, no settings UI. If that turns out to be
false, the abstraction leaked and that is the bug to fix.

## Migrating existing hardcoded copy (plan phase 3)

`scripts/localization-baseline.json` records how much hardcoded copy each `.axaml` still
has. The count may **shrink, never grow**. After extracting a view's copy:

```bash
pwsh scripts/check-localization.ps1 -UpdateBaseline
```

A file that reaches zero drops off the list and is then protected like any migrated file.
