# 064. UI Localization Foundation

## Context

Parlotype's interface is English-only and almost all of its copy is hardcoded. [ADR-056](056-first-run-onboarding-tour.md)
externalized 30 keys for the onboarding tour and the Help section into `Resources/Strings.resx`
and noted that translations would arrive later "as satellite `Strings.<culture>.resx` files;
no markup or code changes needed". Nothing else moved: 211 literal attributes across 26
`.axaml` files, roughly 200 string literals in 48 view models, 18 settings-section titles,
the tray menu, the dialogs and the toasts are all still inline.

Russian and Spanish are wanted first, German and French after. That second half is the
harder requirement — the ninth language has to cost a translation file and nothing else.

Three things had to be settled before any bulk extraction could start, because each is
expensive to revisit once several hundred keys exist.

**The accessor cannot stay hand-written.** ADR-056 wrote `Strings.cs` by hand deliberately,
"so the CLI build stays deterministic under warnings-as-errors". That reasoning holds at 30
keys and collapses at 450.

**Live switching versus restart.** The project mandates `x:CompileBindings="True"` and bans
`{ReflectionBinding}` (CLAUDE.md). A localizer bound through an indexer or a method call is
precisely the shape that ban targets, so live switching looked like it would need a scoped
exemption — and the alternative, a restart prompt, would be the app's second one after
`RuntimePreference`.

**Where user-facing text is allowed to live.** `Parlotype.Core` has zero dependencies and no
resources, yet holds 28 display-name constants across `WhisperModelInfo`, `ParakeetModelInfo`,
`Gemma4ModelInfo` and `WaitTimeOption`.

## Decision

Keep resx and satellite assemblies. `Strings.resx` is the neutral (English) file; each
language adds one `Strings.<culture>.resx`. Keys are flat and area-prefixed
(`Settings_Theme_Title`), continuing the `Onboarding_*` / `Help_*` convention.

**`Strings.cs` is generated** by `scripts/gen-strings.ps1` and checked in. The determinism
argument from ADR-056 is satisfied by the output being a reviewed artefact in git rather than
by a designer running on a developer's machine. Keys containing `{0}` also get a
`Format_<key>(...)` method with one parameter per placeholder, so a call site with the wrong
argument count fails to compile instead of throwing `FormatException` in front of a user.

The `<auto-generated>` header opts the file out of the project's implicit nullable context,
which makes `object?` parameters a CS8669 error under warnings-as-errors — the generator emits
an explicit `#nullable enable` to compensate. This is the concrete form of the hazard ADR-056
anticipated.

**Switching is live, and no `{ReflectionBinding}` exemption is needed.** Avalonia 12 renamed
`Binding` to `ReflectionBinding` and exposes `CompiledBinding.Create<TIn, TOut>(expression, source)`,
which compiles a binding from a lambda in code. Each key gets a `LocalizedString` object with a
plain `Value` property, so `{loc:Tr Key}` returns a *compiled* binding over an ordinary property
access:

```csharp
CompiledBinding.Create<LocalizedString, string>(s => s.Value, Localizer.Instance.Entry(key))
```

An indexer or method lookup would have forced a reflection binding; a per-key object avoids
that entirely and updates each key independently. `Localizer` is a singleton with static state
because a XAML markup extension is constructed by the loader with no access to the DI
container, and the copy it resolves is needed inside DataTemplates, styles and flyouts that no
view model can reach. `UiLanguageService` is the DI-visible seam that drives it.

**`CurrentUICulture` moves; `CurrentCulture` does not.** The interface language is not a claim
about where the user is, so dates, numbers and sort order keep following the Windows regional
settings. A user with an English Windows and a Russian interface still sees their own date
format.

**Copy that view models compose in C# needs an explicit refresh.** Text reaching the screen
through `{loc:Tr}` updates itself; labels built in a constructor do not. `SettingsSectionViewModelBase`
subscribes to `Localizer.CultureChanged` and exposes a virtual `OnCultureChanged()` that
re-raises `Title` by default — the seam every section overrides when it composes its own
labels. `SettingsWindowViewModel` rebuilds the navigation list on the same event, since nav
rows are snapshots.

**`SettingsKeys.UiLanguage`** stores `system` (the default when unset) or a culture name.
`SupportedUiLanguages` in Core is the single registry of shipping languages: the settings
picker and the future parity check both read it, so they cannot drift. A stored language that
a later release no longer ships falls back to the system default rather than pinning the user
to a culture with no resources behind it.

**Language rows are endonyms, never translated.** Someone who has landed in a language they
cannot read needs to find their own in the list, and "Русский" is the only spelling that works
from every other locale. Only the "System default" row is localized, because it names a
behaviour rather than a language.

**Display copy leaves Core.** `WaitTimeOptionExtensions.GetDisplayName` moved to
`WaitTimeDisplayItem` in Desktop; `GetSeconds`, which the pipeline actually runs on, stayed.
The model catalogs keep their English names — "Parakeet TDT v3" and "Large v3 Turbo" are
identifiers, not prose.

## Consequences

Adding a language is one row in `SupportedUiLanguages` plus one resx file. Nothing in markup,
view models or the settings UI changes. Russian and Spanish ship from this ADR onwards with
the 45 keys that exist today already translated, so the invariant "every key in `Strings.resx`
exists in every locale" is true from the start rather than being retrofitted.

Startup blocks briefly on one settings read, and the shape of that read matters:
`JsonFileStore` awaits without `ConfigureAwait(false)`, so awaiting it and blocking on the
result from the UI thread deadlocks before the first window ever appears. The read therefore
goes through `Task.Run` and the culture is applied afterwards, on the UI thread that reads
resources. `LocalizationTests.StartupLanguage_LoadsOnAUiThread_WithoutDeadlocking` covers it —
verified to hang the test host when the pattern is undone.

The interface is now bilingual mid-migration: the Theme and Interface language sections are
translated, everything else is still hardcoded English, so a Russian user sees a mixed
Settings window until extraction finishes. The translated onboarding copy also names UI
controls ("Выход", "Настройки → Приложение → Запуск") that are still drawn in English; both
resolve as extraction proceeds.

`Localizer` is process-wide mutable state, so tests that change the culture have to restore it —
`LocalizationTests` runs in its own non-parallel collection for that reason. A future
localization parity check (key sets, placeholder sets, hardcoded-literal scan) has a stable
registry and a stable generator to build on.
